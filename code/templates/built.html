How this site is built

The engineering behind this portfolio: where the data lives, how it is tested, how it is secured and how I measure it. Every number on this page comes from the code or from a measurement of the live site.

Architecture

  1. BrowserHTML, CSS and plain JavaScript. No framework and no third-party scripts.
  2. Flask appPython on Gunicorn in a Docker container, hosted on Render and deployed from GitHub on every push.
  3. Two databasesSQLite holds the project catalog. Postgres on Neon holds visit analytics, because the host clears its disk on every deploy.

Data and SQL

I chose to build the site's analytics instead of adding a tracker. The browser reports page views, clicks, sections reached, time on page and scroll depth. The server validates each event and stores one row per event.

The reports are plain SQL that runs unchanged on SQLite and Postgres. This query ranks each visit's pages with window functions, so one pass finds where the visit started, where it ended and how many pages it saw:

WITH ranked AS (
  SELECT sid, path, ref, country, device,
         ROW_NUMBER() OVER (PARTITION BY sid ORDER BY ts, pv)           AS first_rank,
         ROW_NUMBER() OVER (PARTITION BY sid ORDER BY ts DESC, pv DESC) AS last_rank,
         COUNT(*)     OVER (PARTITION BY sid)                           AS pages
  FROM events WHERE kind = 'view' AND ts >= ?)
SELECT path, COUNT(*) AS visits
FROM ranked WHERE last_rank = 1      -- the last page of each visit
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;

The same 40 sample visits were run through both databases and every report compared. They matched, and the comparison caught one real bug: Postgres returns SUM as a decimal where SQLite returns an integer.

  • 0cookies set
  • 0IP addresses or personal details stored
  • 4event types: view, click, section, leave

Visitors who turn on Do Not Track or Global Privacy Control are not counted, and neither are crawlers.

Testing

14 automated tests run against a throwaway database. They cover navigation, search and filters, escaped input, SQL injection attempts, analytics validation, the locked stats page and the security headers.

This one posts hostile and malformed events and checks that only the valid ones are stored, with a SQL fragment kept as harmless text:

self.event(kind='admin')                       # unknown event type
self.event(path='https://evil.example')        # not a path on this site
self.event(sid="x' OR 1=1 --")                 # malformed visit id
self.event(kind='click', label="'); DROP TABLE events; --")
rows = self.rows()[before:]
self.assertEqual([r[0] for r in rows], ['view', 'leave', 'click'])
self.assertEqual(rows[2][2], "'); DROP TABLE events; --")

The same habit shows up in my other projects: 433 JUnit tests on TopSecret as a team, and 428 automated tests plus simulated-player runs on Merge a Brainrot.

Security

  • Queries are parameterized. Search text and analytics fields never become part of the SQL itself.
  • A content security policy allows scripts only from this site. The two inline scripts carry a random value that changes on every request.
  • Other headers block framing by other sites, content-type guessing and unneeded device permissions, and require HTTPS.
  • The stats page is private. It does not exist until a password is configured, compares it in constant time and is excluded from search engines.
  • Input is bounded. Event text is length-capped, numbers are clamped and requests over 64 KB are refused.
